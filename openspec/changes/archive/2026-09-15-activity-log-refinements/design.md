## Context

Six independent-but-related refinements to the Agents tab, Logs tab, and project details modal (see proposal.md - Why). Relevant current state:

- `crates/agentmon-proto/src/lib.rs`: `AgentInfo` has `status_since_ms` (resets on every status transition) but nothing tracking when the current run began. `TestRunInfo` has an analogous-looking `run_started_ms`, but its reset trigger doesn't transfer directly: a test run's pid changes on every new run, so "reset on new pid" and "reset on new run" are the same event. An agent's pid is stable for the life of a whole Claude Code session and cycles through many started → running → (needs input →)\* → done turns under that one pid, so "new run" for an agent means "transitioned into running," not "new pid." `LogEntry` has no `pid` field.
- `crates/agentd/src/registry.rs`: `Registry::upsert` creates/updates `AgentInfo` entries and already distinguishes "new entry" vs. "status changed" vs. "same status" to decide whether to reset `status_since_ms`.
- `crates/agentd/src/ingest.rs`: `ingest_event` is the single point that knows both the previous and new status for a transition, calls `should_notify`, and appends to `ActivityLog` - the natural place to add the new independent "started" capture and to populate `LogEntry.pid`.
- `crates/agentmon/src/ui.rs`: `render_agent_table` builds one combined STATUS cell via `project_status_line` (iterating `AGENT_STATUS_ORDER`) and a separate call into test-run rendering, concatenated into the same cell. `render_details_modal` renders Agents/Tests/Logs panes using `status_cell_text_and_style` / `test_run_status_cell_text_and_style` / `log_entry_status_line`, the same helpers the top-level tabs use. `render_logs_tab` and `log_status_cell_text_and_style` render the Logs tab's per-entry label. `log_test_run_duration_ms` already computes a completed test run's Logs-tab duration by scanning backward through `all_logs` for the most recent matching "started" entry for the same project - this is the pattern the new agent "done" duration in the Logs tab reuses.

## Goals / Non-Goals

**Goals:**
- Give every "done"/"needs input" log entry a corresponding "started" entry to bound it, without tying that capture to the notification path (which intentionally excludes "running" transitions today).
- Make the live row's "done" duration and the Logs tab's "done" duration each correct on their own terms - the row from a persisted daemon-side timestamp (robust to log eviction), the log view from log-entry history (consistent with how test-run durations already work there).
- Keep the Agents/Tests column split, pid display, emoji fix, and prefix rules purely presentational changes with no daemon protocol impact beyond the two additive fields already planned.

**Non-Goals:**
- Notifying the user (sound/banner) when an agent starts. The request only asks for log/column visibility, not a new notification class; adding one would roughly double notification volume for every active session.
- Retroactively backfilling "started" entries for agents already mid-session when this ships - the log is a live-forward capture, not a reconstruction from registry state.
- Deduplicating "started" log growth against the existing 500-entry global cap - the cap already exists and evicts oldest-first; doubling roughly the agent-side entry rate simply means the log's effective time window shrinks somewhat, which is an acceptable, self-correcting consequence rather than a new mechanism to build.

## Decisions

**`run_started_ms` lives on `AgentInfo`, reset on every transition into "running" - not on entry creation alone, and not on pid replacement alone.** This is the one place the test-run analogy actively misleads: `TestRunInfo.run_started_ms` resets on a new pid because a test run's pid *is* one run. An agent's pid survives across many turns, so pinning `run_started_ms` to entry-creation-or-pid-replacement (the first draft of this design) would leave it stuck at the very first turn's start forever - every subsequent "done" duration would measure from session start, not from that turn's start, growing more wrong with each cycle. The correct reset trigger is the same event that already resets `status_since_ms` on entry into running specifically: `Registry::upsert` sets `run_started_ms = now` whenever the previous status differs from `Running` and the new status is `Running` (including "done -> running", which the status-since logic already treats as an ordinary transition), and leaves it untouched on every other transition (including out of running, and between two non-running statuses). It's still set at entry creation as a sane initial value for entries that don't start in "running". Keeping it server-side (rather than deriving it from the log) means the "done" duration on the live row survives activity-log eviction and TUI reconnects, the same robustness `status_since_ms` already has. Alternative considered: compute the row's "done" duration purely from the Logs tab's `started` entry the same way `log_test_run_duration_ms` does. Rejected because the Agents tab's row-level duration must work even when the matching "started" entry has scrolled out of the bounded log (long-lived, high-turn-count sessions).

**"Agent started" logging keys off the transition itself, in `ingest_event`, not off a new registry field.** `ingest_event` already receives the previous status (to decide `should_notify` and status-since reset); a new independent check - "does this transition move status to Running from something else, or is this a brand-new entry whose first status is Running?" - appends an `agent`/`started` `LogEntry` regardless of `should_notify`'s outcome. This is deliberately decoupled from the notification path (unlike today's activity-log requirement, which only fires at notification points) because there is no notification to piggyback on and the user's ask is purely about the log/columns, not sound/banners. Alternative considered: derive "started" client-side in the TUI by watching for a `running` `AgentUpdate` after a non-running status. Rejected - the TUI has no durable log-append semantics (it just renders whatever `LogAppended`/`Snapshot` it's given), so this logic belongs server-side where the log itself is authoritative and bounded.

**`LogEntry.pid: Option<u32>`, populated whenever known at the call site, rendered only where the spec asks for it.** Both `AgentEvent` and `ReportTestRun` already carry a `pid` at the point a `LogEntry` is constructed, so populating the field costs nothing extra in `ingest.rs`. Making it `Option` (rather than requiring test-run entries to fabricate one) keeps the type honest about what's semantically available; the TUI only renders it in the details modal's Agents pane and agent-category Logs-pane rows, per the accepted scope - the top-level Logs tab and Agents-tab cells stay exactly as wide as they are today.

**Agents/Tests column split reuses the existing per-status-segment rendering, just routed into two `Cell`s instead of one.** `project_status_line`'s per-agent-status segment logic (iterate `AGENT_STATUS_ORDER`, emit one styled segment per distinct status present) is unchanged; only the table's `Row` construction changes, from `[project, combined_status, updated]` to `[project, agents_cell, tests_cell, updated]`, with the width-allocation logic in the column-sizing constraint code updated to split what was previously "STATUS"'s share between the two new columns (proposal reserves the same total proportion, split between them, rather than inventing a new sizing ratio - avoids relitigating the existing wide-terminal/narrow-terminal width tests beyond updating their column-count expectations).

**Category-word prefix and pane-conditional omission is a formatting-function parameter, not two copies of the label logic.** `status_label_and_style` / `test_run_status_cell_text_and_style` / `log_entry_status_line` each gain a `with_category_prefix: bool` (or equivalent) argument rather than being duplicated for "tab" vs. "pane" call sites - the Agents tab and Logs tab pass `true`, the details modal's Agents/Tests panes pass `false`, and its Logs pane passes `true`. This keeps the single source of truth for emoji/color/duration per status while letting the one new axis (prefix) vary by call site, consistent with how duration already varies by status within the same functions.

**Stale emoji: 🕸️ → 👻, a one-line constant change.** 🕸️ is U+1F578 + U+FE0F (VS16); some terminal fonts fall back to a narrow glyph for the base codepoint despite the selector, which is the half-width/highlight-corruption bug reported. 👻 (U+1F47B) has default emoji presentation with no variation selector needed, so it doesn't depend on a terminal correctly honoring VS16.

## Risks / Trade-offs

- [Risk] Doubling the rate of agent-category log entries (every turn now logs both "started" and "done"/"needs input") shrinks the effective time window of the existing 500-entry global cap faster than before. → Mitigation: accepted as self-correcting per Non-Goals; no cap-size change is in scope, and the cap already evicts oldest-first regardless of category mix.
- [Risk] A "declined -> running" or "stale -> running" transition logging "started" could read oddly if a user expects "started" to mean only "brand-new session," not "resumed from a terminal-looking state." → Mitigation: this matches the literal transition-into-running rule the spec states plainly, and errs toward more visibility (a start marker before every subsequent done/needs-input) rather than under-logging, which was the original complaint.
- [Trade-off] The Logs tab's "done" duration (computed by scanning back through log entries for a same-project "started") and the Agents tab row's "done" duration (computed from the persisted `AgentInfo.run_started_ms`) are two independently-computed numbers that could disagree if the matching log entry was evicted from the 500-entry cap before the task finished. → Accepted: this is the same trade-off the test-run duration already lives with today (`TestRunInfo.run_started_ms` vs. log-derived duration), not a new class of inconsistency introduced by this change.
- [Risk] Resetting `run_started_ms` on every transition into running - including resuming from "needs input" or "declined" mid-turn, not only from "idle"/"done" - means a "done" duration measures from the *most recent* resumption, not from the whole turn's true beginning if it was interrupted by a permission prompt along the way. → Accepted: this mirrors how the existing "running" live duration already resets on any transition out of and back into running (see the "A status transition resets the displayed duration" scenario), so "done"'s fixed duration stays consistent with that established behavior rather than introducing a second, more complex accounting rule just for the terminal case.
