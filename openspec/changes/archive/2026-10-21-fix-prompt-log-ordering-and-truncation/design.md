## Context

See proposal.md for motivation. This covers two independent pieces: the actual root cause of the still-inverted "started before prompt" ordering (the prior `improve-prompt-log-entries` change fixed a real bug but not the one causing the user's "consistently" report), and the two Logs-tab/modal rendering defects (missing space, fixed-length truncation).

**Why the previous ordering fix didn't close the gap - traced through the actual code:**
- `improve-prompt-log-entries` added `EventSequencer` (`crates/agentd/src/server.rs`): each connection is handed a ticket (`next_ticket`) the moment `serve`'s single-threaded accept loop accepts it, and a `ReportEvent` connection's `wait_for_turn(seq)` blocks until every earlier ticket's `complete` has been called, so **application** order is guaranteed to match **accept** order. This part works and is unaffected by this change.
- The gap is upstream of accept order itself. `agentmon-report::main.rs::run_report` calls `read_and_build_event(io::stdin(), ...)` - which calls `input.read_to_string(&mut raw)`, reading all of stdin to completion and then `serde_json`-parsing it - and only afterward calls `send_event`, which is where `UnixStream::connect` happens (`report.rs::send_event`). So a hook's agentmon-report process does not even attempt to connect until it has finished reading and parsing its own payload.
- A `UserPromptSubmit` payload carries the full submitted prompt text (`HookPayload.prompt`); a `PreToolUse` payload carries a handful of short fields. Reading and `serde_json`-parsing the former is measurably slower than the latter. Since `connect()` (and therefore the daemon's `accept()`, and therefore the ticket) only happens after that read+parse step, the `PreToolUse` event's connection can - and, per the user's report, consistently does - reach the daemon's accept loop before the `UserPromptSubmit` event's connection, even when Claude Code invoked `UserPromptSubmit`'s hook first. `EventSequencer` faithfully preserves this (already-wrong) accept order; it has no way to know it's wrong.
- This is exactly the residual risk `improve-prompt-log-entries`'s design.md flagged but couldn't pin down without more evidence ("if misordering is still observed after this ships, that would point to something outside what was found here"). This is that fresh look.

**Existing width-aware truncation pattern to reuse** (`crates/agentmon/src/ui.rs`):
- `truncate_line(line: Line<'static>, max_width: usize) -> Line<'static>` already does exactly what's needed: measures display width (not char count, so double-width emoji are accounted for), truncates to `max_width - 3` and appends `...` only when the content actually overflows, and treats `max_width == 0` as "no limit." It's already used by `render_reminders_pane` and the Agents tab's AGENTS/REMINDERS columns.
- The details modal's Logs pane already resolves its STATUS column's real width before calling `truncate_line`: `let columns = Layout::horizontal(widths).spacing(1).split(inner); let status_width = columns[2].width as usize;` (mirrored from `render_reminders_pane`'s own comment about replicating `Table`'s column-width resolution, including the 1-column inter-column spacing a bare `Layout::split` doesn't add on its own).
- The top-level Logs tab (`render_logs_tab`) builds its STATUS `Cell` content (via `log_entry_status_line`) *before* any layout resolution happens, and never calls `truncate_line` on it at all - it relies entirely on `prompt_snippet`'s fixed `PROMPT_SNIPPET_MAX_CHARS = 50` to keep the string short, and lets Ratatui's `Table` clip anything still-too-long silently (no ellipsis). This is the second half of the gap: even resolving the real width doesn't help today's Logs tab unless the snippet-building step and a `truncate_line`-style call both move to happen after that resolution.

## Goals / Non-Goals

**Goals:**
- Make the daemon's already-correct accept-order-preserving logic actually receive a correct accept order, by changing when `agentmon-report` opens its connection relative to reading/parsing its payload - without adding any new wire message or protocol field.
- Make a prompt entry's marker and snippet visibly separated by one space, consistently in the Logs tab and the details modal's Logs pane.
- Make prompt and last-prompt-snapshot snippets use the real rendered STATUS column/pane width (reusing `truncate_line`, the same mechanism already used elsewhere in this file) instead of a fixed character constant, in both the Logs tab and the details modal's Logs pane.

**Non-Goals:**
- No change to the `EventSequencer`/ticket mechanism itself - it is correct and stays as-is; only when a ticket gets claimed changes.
- No change to `AgentEvent`/`ClientMessage`/`ServerMessage` (`agentmon-proto`) - purely a timing change in `agentmon-report` and a rendering change in `agentmon`.
- No general change to how other `ClientMessage` variants (`ReportTestRun`, reminder commands, etc.) connect - this only touches the `ReportEvent` path's client-side ordering.

## Decisions

**Connect before reading stdin, send once parsed:** `run_report` opens the `UnixStream` to the daemon immediately (right after determining `host_context`/`pid`, before touching stdin), then reads and parses stdin, builds the `AgentEvent`, and writes it onto the already-open stream. Concretely, `report::send_event`'s connect step and its write step split into two: a `connect(socket_path) -> io::Result<UnixStream>` called first, and a `send_on(stream, event) -> io::Result<()>` called once the event is built. If stdin read/parse fails or produces no trackable event (`build_event` returns `None`), the already-open connection is simply dropped without writing anything - which `agentd::server::handle_connection` already treats as "connection closed before a message arrives," a no-op that still releases the connection's `EventSequencer` ticket (`sequencer.complete(seq)` runs whether or not a message was read). No daemon-side change is needed for this to work correctly.
  - *Alternative considered:* Have the daemon assign tickets based on a timestamp the hook includes in its payload instead of accept order. Rejected: Claude Code's hook payloads carry no such ordering signal, and introducing one would require coordinating a clock or counter across independent hook subprocesses with no shared state - far more complex than just connecting earlier.
  - *Alternative considered:* Keep connecting late, but have the daemon peek at the message type via a cheap pre-read (e.g. a 1-byte discriminant sent before the full payload) so smaller messages don't jump the queue. Rejected: this still requires the client to decide what to send before its slow work is done, which is the same reordering problem one level down, and adds protocol complexity for no benefit over simply connecting first.

**Logs tab resolves its STATUS column's real width before building row text, mirroring the modal:** `render_logs_tab` computes the same kind of `Layout::horizontal(widths).split(inner)` (or equivalent) the details modal's Logs pane already uses, extracts the STATUS column's resolved width, and threads it into `log_entry_status_line`/`prompt_snippet` so the snippet is sized against that real width and `truncate_line` (or an equivalent width-aware cut) is applied the same way the modal already does - rather than the fixed `PROMPT_SNIPPET_MAX_CHARS` constant. `prompt_snippet` changes from a fixed-constant function to one taking a `max_width: usize` parameter (flattening whitespace unchanged, truncation width-aware via the same display-width logic `truncate_line` already uses, so emoji-containing prompts are not undercounted). The modal's existing `status_width` resolution is reused as-is and threaded through the same way.
  - *Alternative considered:* Leave the Logs tab's `Constraint::Fill(1)` STATUS column unresolved and just raise `PROMPT_SNIPPET_MAX_CHARS` to a larger fixed number. Rejected: this only moves the mismatch to a different fixed point - a very wide terminal would still waste space, and a very narrow one could still let Ratatui silently clip without an ellipsis (today's actual failure mode on a narrow terminal). Resolving the real width fixes both ends.

**Space insertion is a one-line change at the source of the marker/snippet join:** `log_status_cell_text_and_style`'s `LogCategory::Prompt` arm keeps returning just the marker, but `log_entry_status_line`'s prompt-category branch changes from `text.push_str(&prompt_snippet(prompt))` to `text.push_str(&format!(" {}", prompt_snippet(prompt, available_width)))` (or equivalent) - i.e. the space is part of the snippet-joining step, not baked into the marker constant, so every caller of the marker-only helper is unaffected.

## Risks / Trade-offs

- [Connecting before reading stdin means a hook process now holds a daemon connection open for the duration of its own stdin read/parse, instead of only for the brief write] -> Acceptable: the daemon's per-connection `READ_TIMEOUT` (500ms) already bounds how long any connection can be held, and `agentmon-report`'s own stdin reads are local pipe/file reads with no network latency - well within that bound in practice. If a payload read legitimately needs more than 500ms (unexpected), the connection times out and is dropped exactly like today's malformed-payload case, same user-visible behavior (the hook is never blocked - `send_event`'s own timeouts are unchanged).
- [This fix narrows the race to "whichever of two hook subprocesses calls connect() first," which still assumes Claude Code starts (or at least begins executing) the subprocess for an earlier-fired hook before the subprocess for a later-fired one - reasonable, but not something this change can independently verify against Claude Code's actual process-spawning behavior] -> Flagged for the user directly, same as the prior change's equivalent risk: if misordering is still observed after this ships, that would point to Claude Code's own hook-subprocess-spawning behavior rather than anything in this codebase, and would need a fresh look with that evidence in hand.
- [Threading a width parameter through `prompt_snippet` and `log_entry_status_line` changes their signatures, touching every existing call site (including tests)] -> Contained: all call sites are within `crates/agentmon/src/ui.rs` itself (and its own `#[cfg(test)]` module), so this is a local, mechanical signature change with no cross-crate impact.

## Migration Plan

No data migration or protocol version bump. Both crates (`agentmon-report`, `agentmon`) ship together as part of the same release, as usual. No rollback concern beyond reverting the commit - no persisted state changes shape.
