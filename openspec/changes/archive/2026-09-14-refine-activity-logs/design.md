## Context

Three independent problems, found by using the Logs-tab/unified-row feature in real long-running sessions (see proposal.md - Why):

1. **Invisible "running" status.** `crates/agentmon/src/ui.rs` defines `SELECTED_ROW_BG: Color = Color::Blue` for the Agents tab's row-highlight background, and separately defines the "running" status's style as `Style::new().fg(Color::Blue)` (`status_label_and_style`). `render_agent_table` always has a selected row once any project row exists - `TableState::default().with_selected(...)` is set to `Some(0)` (clamped) even before the user has pressed a navigation key - so a project whose only status is "running" renders blue-on-blue on the very row a user is most likely looking at right after starting a fresh agent. The details modal (`render_details_modal`) doesn't apply a row-highlight background at all, which is why status renders correctly there and made this look like a modal-vs-table inconsistency rather than a color collision.

2. **Transient duplicate/flip-flopping project row.** `crates/agentd/src/registry.rs`'s `Registry::upsert` dedups by pid only when the incoming event's session id is new to the registry (`previous_status.is_none()`): it drops any *other* entry sharing that pid. This was added in `2026-09-01-fix-duplicate-agent-entries-on-clear` to handle `/clear` reusing a pid under a new session id. It has no memory of session ids it has already retired - once session A's entry is removed in favor of session B, a later event that still names session A looks, from the registry's point of view, exactly like a brand-new session that happens to share B's pid. That late event (a hook process that was slow to launch, or an out-of-order delivery - hook events are one-shot, independently-connecting processes per `agentd`'s design, handled on separate server threads, so there is no ordering guarantee between them) re-registers A and, by the same-pid rule, evicts the live B entry. The TUI then shows two rows fighting over one project (A reappearing, B's row vanishing) until whichever session's events "win" the race settles down - matching the reported flicker, the mismatched Agents/Logs views (each event still gets logged under whichever session/cwd was live at that instant), and the eventual self-healing once new events stop naming the dead session.

3. **Empty-state text placement.** Already-established precedent: the Logs tab puts "No activity matches the current filter" as gray body text (`ui.rs:206-218`), not in the title. The Agents tab's "no agents tracked yet" and the Logs tab's own "no activity logged yet" currently live in the block title instead (`ui.rs:128-134`, `177-181`), which is the inconsistency called out in the request.

## Goals / Non-Goals

**Goals:**
- Make "running" legible on a highlighted row without weakening the "status survives selection" intent the current highlight design already states (see `SELECTED_ROW_BG`'s doc comment).
- Close the specific resurrection path in (2): a late event for a session id already superseded on its pid must be a no-op, not a re-registration.
- Align the two remaining title-based empty states with the existing gray-body-text convention.

**Non-Goals:**
- General reordering/at-least-once delivery guarantees for hook events. Events remain one-shot, independently-connecting reports; this change only makes the registry robust to *arrival order* for the one specific case (a pid's session id changing) that already has dedup logic, not a general event-sequencing overhaul.
- Changing which statuses get which colors beyond resolving the one collision (Running vs. the highlight background). The other five status colors don't collide with `SELECTED_ROW_BG`.
- A UI toggle or setting for the empty-state text; it's a fixed placeholder like the existing filter-mismatch message.

## Decisions

**Highlight collision - move the highlight color, not the status color.** Change `SELECTED_ROW_BG` to a color not used by any of the six agent-status or three test-run-status styles (Blue/Running, Gray/Idle, Yellow/NeedsInput, Green/Done, DarkGray/Stale, Red/Declined, plus Blue/Started, Green/Passed, Red/Failed). Changing the highlight avoids touching nine status styles (and their tests) to dodge one collision, and keeps "running" on the same blue it's had since `2026-09-08-add-status-emojis`. Add a unit test asserting no status style's foreground equals `SELECTED_ROW_BG`, so a future status color addition can't reintroduce the same class of bug silently.

**Superseded-session tracking - a bounded, global tombstone set in `RegistryState`, not a permanent record.** `RegistryState` gains a global (not per-pid) record of session ids retired by the same-pid dedup, capped at `MAX_SUPERSEDED_SESSIONS` (256) and evicting the oldest tombstone once exceeded - the same bounded-eviction shape `ActivityLog` already uses. `upsert` checks membership in this set before treating a session id as brand-new: if the incoming session id is a known tombstone, the event is dropped entirely (no registry change, no notification, no log entry - it's stale information about a session that no longer exists), returning whichever entry currently holds that pid unchanged. This is scoped to the same mechanism the 09-01 fix already introduced, rather than a general "reject out-of-order events" framework, since that's the only place a resurrection can currently happen. A per-pid cap (remembering only the single most-recently-superseded id for each pid) was considered first but rejected: it fails the case where a pid is superseded twice in succession (session A -> B -> C) - by the time a late event for A arrives, the per-pid record has already been overwritten to remember only B, so A would be wrongly resurrected and evict C. A global set keyed by session id (not pid) has no such blind spot, since session ids are effectively unique regardless of which pid retired them.

**Empty-state text - reuse the existing gray-placeholder pattern exactly.** Both `render_agent_table` and `render_logs_tab` already compute an `inner` rect and know how to draw body text beneath the header (the Logs tab does this today for filter mismatches). Route the "nothing tracked yet" / "nothing logged yet" cases through the same body-paragraph technique instead of folding the message into the title string, and drop the corresponding `banner`-independent title branches. The Logs tab's title keeps rendering its sort/filter hint unconditionally, matching the modified spec.

## Risks / Trade-offs

- [Risk] A different, not-yet-added status could be assigned a color that again collides with whatever `SELECTED_ROW_BG` becomes. → Mitigation: the new "no status matches the highlight color" unit test fails immediately if that happens, at the same layer where status colors are already asserted distinct from one another.
- [Risk] The tombstone set could itself grow unbounded if many pids churn through `/clear` over a long daemon lifetime. → Mitigation: cap the set at `MAX_SUPERSEDED_SESSIONS` (256), evicting the oldest tombstone once exceeded, so memory stays flat regardless of total historical churn. A late event arriving after 256 more supersessions have occurred elsewhere would no longer be recognized as stale - accepted as a generous enough window in practice, since the race this guards against resolves in seconds, not after hundreds of intervening `/clear`s.
- [Trade-off] A genuinely new session that, by coincidence, reuses both an old pid (recycled by the OS) and happens to collide with a tombstoned session id for that same pid would be dropped as if it were the late event. This is accepted as vanishingly unlikely (session ids are Claude Code-generated, effectively unique) and strictly better than the current behavior, which mishandles the far more common case (an actual late duplicate).
