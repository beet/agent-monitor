## Context

See `proposal.md` for motivation. Relevant current shapes:

- A "project" has no entity of its own anywhere in the system. It is purely `project_name(cwd)` (`crates/agentmon/src/ui.rs:1034` and an identical copy in `crates/agentmon/src/app.rs:1159`) - the working directory's final path segment - called wherever a project needs to be displayed, sorted, filtered, or compared: the Agents tab, the Logs tab, the Reminders tab, the details modal title, every cycle-filter, and the Agents-tab search.
- Every piece of daemon state (`Registry`'s agents and test runs, `ReminderRegistry`'s reminders, `ActivityLog`'s entries) lives only in process memory and is discarded on daemon restart; there is no file-backed persistence anywhere in `agentd` or `agentmon` today, and the user has confirmed a custom project name should follow that same lifetime rather than introduce the project's first persistence mechanism.
- The `ClientMessage`/`ServerMessage` protocol (`crates/agentmon-proto/src/lib.rs`) is entirely fire-and-forget for mutations: `CreateReminder`, `UpdateReminder`, `DeleteReminder`, `StartReminder`, `StopReminder` have no synchronous reply. A request the daemon can't honor (e.g. `CreateReminder` past the per-project cap) is silently dropped - `crates/agentd/src/ingest.rs`'s `ingest_create_reminder` returns `None` and `server.rs` just logs to stderr, sending the client nothing. There is no precedent anywhere in this protocol for a unicast success/failure reply to one client.
- Every connected client already receives, via `Snapshot` on connect and incremental pushes after, every agent, test run, log entry, and reminder the daemon knows about - which is also every working directory the daemon knows about. A client's own state is therefore already a complete mirror of the daemon's for the purpose of knowing "every project currently known."
- The existing `ReminderForm` (`crates/agentmon/src/app.rs`'s `ReminderForm`/`ReminderFormMode`/`ReminderFormField`, driven by `crates/agentmon/src/input.rs`'s `handle_reminder_form_key`) is the closest existing analog for a modal text-entry form: `Esc` discards, `Enter` submits and returns the `ClientMessage` to send, typed characters and `Backspace` edit the focused field. It is scoped to the details modal (only reachable once `Modal::Details` is open) and has no client-side validation or inline error display - there is no precedent in this codebase for a form that rejects its own input before sending anything.

## Goals / Non-Goals

**Goals:**
- Let the user attach a custom display name to a project (working directory) that replaces the directory-derived name everywhere a project name is shown, sorted, or filtered.
- Keep the mutation fire-and-forget, matching every other `ClientMessage` in this protocol, while still giving the user immediate, correct feedback on invalid input (blank, or a name that collides with another project) without a new request/response mechanism.
- Make every existing view that resolves a project's name - including historic activity-log entries - pick up a rename retroactively, since none of them store a name of their own; they all already re-derive it from the working directory on the fly.

**Non-Goals:**
- No persistence of custom names across a daemon restart (see Context).
- No rename of the underlying working directory, git worktree, or branch - this only changes what the TUI displays.
- No change to how a project's identity is keyed; it remains the exact working-directory path, same as every other per-project concept (agents, test runs, reminders, log entries).
- No multi-client conflict-resolution UX. Two `agentmon` instances renaming the same or colliding project at the same instant is a real but narrow race (see Risks); it is handled by dropping the losing request, not by surfacing a conflict to the user.

## Decisions

**The daemon's `Registry` gains a `cwd -> String` custom-name map; absence of an entry means "use the directory-derived default."** This mirrors how `project_name(cwd)` already works (always computed, never stored) and keeps storage proportional to the number of projects actually renamed rather than requiring every project to be pre-populated with a name the moment it's first seen.

**Protocol: a new fire-and-forget `ClientMessage::RenameProject { cwd: PathBuf, name: String }`, applied and broadcast as `ServerMessage::ProjectRenamed { cwd: PathBuf, name: String }` to every connected client (including the one that sent it) - no unicast reply.** This matches every other mutation in the protocol. `Snapshot` gains a `project_names: Vec<ProjectName>` field (new struct `ProjectName { cwd: PathBuf, name: String }`) carrying every currently-renamed project, so a client that connects after a rename still sees it, the same way `Snapshot.reminders` carries every currently-tracked reminder. `ProjectRenamed` is also how the single map entry is added or changed; there is no separate "remove a rename" operation in this change - the user can always rename back to the directory-derived default name to approximate reverting (with the known limitation that doing so stores that string as the custom name rather than clearing the override, which only matters if comparing identity rather than displayed text; nothing in this change actually cares about that distinction).

**Validation (non-blank, unique among all known projects) is enforced client-side, before `RenameProject` is ever sent - the daemon re-validates the same two rules defensively but has no way to report a rejection back, so an invalid request that somehow reaches it (only possible via a race - see Risks) is silently dropped, exactly like a `CreateReminder` past its cap.** The client already holds a complete mirror of every project the daemon knows (Context, above), so it can enforce "unique across every known project, including ones never renamed" without any new round trip. This keeps the protocol's fire-and-forget shape intact and gives the user inline, immediate validation feedback - which a round trip to the daemon could not do any faster anyway.
  - *Alternative considered*: have the daemon validate and reply with success/failure. Rejected because it would introduce the first request/response pairing in a protocol that is otherwise entirely either fire-and-forget (mutations) or server-push (state updates), to solve a problem the client can already solve locally with data it already has.
- A submitted name is trimmed of leading/trailing whitespace before either check; a name that is empty after trimming fails the "non-blank" rule.
- Uniqueness compares the trimmed submitted name, exact case, against every other known project's *effective displayed name* (its custom name if it has one, otherwise its directory-derived default) - excluding the project being renamed itself, so resubmitting a project's own current name is accepted as a no-op rather than rejected as a duplicate of itself.
- "Every known project" is the union of every working directory appearing in the client's tracked agents, test runs, log entries, or reminders, plus every key already in the custom-name map (covering a renamed project whose agents/test-runs/reminders have since been cleared and whose log entries have aged out of the activity log's bounded retention - the rename should not become un-collideable just because everything else about that project happened to scroll away).

**`project_name(cwd)` becomes `project_name(cwd, names)`, threading the custom-name map through every existing call site, rather than a new parallel helper.** Both copies of this helper (`ui.rs` and `app.rs`) already exist solely to compute a display string from a `PathBuf`; adding the override lookup at their one definition point is what makes every existing caller - Agents tab, Logs tab, Reminders tab, details modal title, every sort/filter/search - correct for renamed projects with no per-call-site change, including historic log entries, which already call this same helper at render/query time rather than storing a name on the `LogEntry` itself.

**The rename form is a new, independent piece of `App` state (`rename_form: Option<RenameForm>`), not nested inside `Modal`, mirroring `reminder_form`'s shape but reachable without the details modal being open first.** `ReminderForm` can only be opened from inside `Modal::Details`, but this feature's Agents-tab shortcut must work with no modal open at all. Keeping it a sibling optional field (checked for in `handle_key` before the `app.modal.is_some()` dispatch, the same way `agents_search_editing` already is) lets it overlay either the bare Agents tab or an already-open `Modal::Details` without `Modal` needing a variant that means two different things depending on what's underneath it.
  - Critically, this check must also come *before* `handle_key`'s global `KeyCode::Char('q')` -> `Quit` check, not merely before the `app.modal.is_some()` dispatch - the same placement `agents_search_editing` already uses, and for the same reason: a project name is free-text the user types, and "q" is a plausible character to want in one (e.g. "queue-123"). `reminder_form`'s own Name field does not get this protection today (it is only reachable from inside `Modal::Details`, which is checked after the global `q` quit), so typing "q" while editing a reminder's name already quits the app - a pre-existing quirk this change does not fix, but must not newly replicate for project names, since unlike a reminder's name, a project's name is the very thing this feature exists to let the user type freely.
  - A newly-written `rename_form_input_char` must therefore not special-case `q` away from the character it appends - it simply needs to run before `handle_key` ever reaches the `q` check, which the routing above already guarantees.
  - `RenameForm { cwd: PathBuf, name: String, error: Option<String> }`. `error` is set by the client-side validation above when `Enter` is pressed on invalid input, cleared on any subsequent edit, and never set by anything the daemon sends back (there is nothing for it to send back).
  - Opened from the Agents tab: scoped to the currently-selected row's project. Opened from within the details modal: scoped to that modal's project, reachable regardless of which pane (Logs/Reminders) currently holds focus - matching how `R` (new reminder) already works regardless of focus.
  - `Esc` discards the form with no message sent, matching `ReminderForm`. `Enter` validates; on failure, sets `error` and keeps the form open with the user's text intact; on success, sends `RenameProject` and closes the form - the UI "refreshes" the moment the resulting `ProjectRenamed` broadcast is applied, the same as every other server push already does, not as a special case for this form.

## Risks / Trade-offs

- **A race between two connected clients renaming at nearly the same instant can let a duplicate through.** Client-side validation is checked against each client's *last-synced* view, which is momentarily stale the instant another client's rename lands first. Mitigation: the daemon re-checks both rules at apply time and drops a request that's no longer valid by then, so the daemon's own map never ends up with a duplicate or blank entry - the losing client's form simply doesn't see its change reflected back (no `ProjectRenamed` for it arrives), which reads as "nothing happened" rather than an explained conflict. Accepted as a narrow, low-stakes edge case consistent with how this protocol already treats every other silently-dropped rejection.
- **Renaming is forgotten on every daemon restart**, same as every other piece of daemon state - explicitly accepted by the user (see proposal.md) rather than a limitation discovered after the fact.
- **Two unrelated projects that happen to share a directory basename can now collide on uniqueness even though neither was ever renamed**, since the default name participates in the uniqueness check. This is the proposal's explicit requirement ("unique... including projects that have not been renamed"), not an incidental side effect.
