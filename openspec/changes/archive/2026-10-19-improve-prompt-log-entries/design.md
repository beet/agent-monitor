## Context

See proposal.md - Why/What Changes for motivation. This covers three independent pieces: the daemon's event-ordering fix, the Logs-tab/Logs-pane prompt-entry text change, and the new full-prompt modal - plus the facts that pinned down the ordering bug's actual root cause.

**How the ordering bug was confirmed, not just guessed at:**
- `crates/agentd/src/server.rs::serve` accepts connections with `for stream in listener.incoming() { ... thread::spawn(move || handle_connection(stream, ingestor, broadcaster)); }` - every `ReportEvent` (one per Claude Code hook invocation; `crates/agentmon-report/src/report.rs::send_event` opens a fresh `UnixStream` per call) is read, parsed, and applied to the registry/activity log (`Ingestor::ingest_event`) on its own independently-scheduled OS thread, with no ordering coordination across connections.
- For a *single* `ingest_event` call, the "prompt before started, same timestamp" pairing (`crates/agentd/src/ingest.rs` lines ~84-121) is correct and already covered by passing tests (`a_prompt_that_starts_a_run_is_recorded_before_the_started_entry`, and the TUI-side `a_same_timestamp_prompt_entry_sorts_ahead_of_the_started_entry_it_precipitated`). There is no bug in that pairing logic itself.
- The only mechanism that can invert "prompt" ahead of "started" is therefore two *separate* `ReportEvent` connections for the same new agent (e.g. the `UserPromptSubmit` event and a `PreToolUse` event fired moments later for the run it starts) being applied out of the order Claude Code's hooks actually fired, because each is independently threaded. A `UserPromptSubmit` payload carries the full prompt text and so takes measurably longer to read off stdin and `serde_json`-parse (in `agentmon-report`, before it even connects) than a `PreToolUse` payload's few fields - exactly the kind of latency difference that lets two independently-scheduled threads finish out of send order even when the connections themselves were accepted in the correct order.
- Hooks themselves are not the problem: Claude Code fires them in the correct logical sequence, and nothing about hook configuration needs to change. This answers the proposal's open question from the user: the gap is entirely on the daemon's side.

**Existing overlay/modal patterns to follow for the new full-prompt modal** (`crates/agentmon/src/app.rs`, `crates/agentmon/src/input.rs`):
- `App.modal: Option<Modal>` holds the single "big" modal (`Details`/`Help`/`QuitConfirm`).
- `App.reminder_form` and `App.confirm_delete_reminder` are *independent* `Option` fields that layer a narrower overlay on top of `Modal::Details`, each peeling back on its own `Esc` without disturbing `app.modal` underneath - checked ahead of (`reminder_form`) or inside (`confirm_delete_reminder`) the main key-dispatch in `input.rs::handle_key`/`handle_modal_key`.
- `App.visible_logs().get(self.logs_pagination.selected)` resolves the Logs tab's current selection; `App.project_logs(cwd).get(self.modal_logs_pagination.selected)` is the equivalent for the details modal's Logs pane (used today by `open_details_modal`).
- `prompt_snippet`/`PROMPT_SNIPPET_MAX_CHARS` (`crates/agentmon/src/ui.rs`) is the existing truncation check - whether a given `LogEntry.prompt` round-trips unchanged through `prompt_snippet` is exactly "is this entry's snippet truncated."
- The modal's Logs pane only *renders* a selection (and so only lets `Enter` act on a specific entry) when it needs to paginate: `render_details_modal` (`crates/agentmon/src/ui.rs`) computes `let selected = if paginated && matches!(app.modal_focus, ModalFocus::Logs) { Some(...) } else { None };` - the `paginated &&` half of that condition means a project with only a handful of log entries (the common case) shows no highlighted row at all, with nothing for `Enter` to target. `App.modal_logs_pagination`'s index itself is already always valid regardless of `paginated` (`Paginator::display_selected`/`display_top` don't depend on it) - the gap is purely in this render-time decision of whether to surface that index as a visible selection.

## Goals / Non-Goals

**Goals:**
- Make the daemon's registry/activity-log updates apply in the order Claude Code's hooks actually fired, for events delivered over independently-accepted connections, without serializing (and thereby delaying) the socket I/O itself.
- Keep today's per-connection-thread isolation for reading/parsing a connection's payload - a slow or hung connection still must not stall unrelated agents' events from being accepted and applied.
- Reuse the existing overlay-layering pattern (independent `Option` field, not a new `Modal` variant) for the full-prompt view, so it composes with `Modal::Details` the same way `reminder_form` already does.

**Non-Goals:**
- No new wire message or `ClientMessage`/`ServerMessage` variant - this is purely an internal daemon-side ordering and TUI-rendering change.
- No change to hook configuration (`crates/agentmon-report/src/install_hooks.rs`) - confirmed unnecessary per the Context section above.
- No general-purpose "scrollable modal" abstraction - the full-prompt modal's scrolling is self-contained, not shared with the Last Prompt pane (which deliberately stays truncate-only, non-interactive, per its existing spec).

## Decisions

**Ordering fix - a ticket/turnstile apply step, not a single serialized worker:** each connection thread still reads and `serde_json`-parses its `ReportEvent` independently and concurrently (unchanged). Immediately after `listener.incoming()` accepts a connection, the accept loop hands out the next sequence number from an `AtomicU64` (or equivalent) *before* spawning that connection's thread - so sequence number order is accept order by construction. Each connection thread, once it has finished parsing its event, waits (via a small `Mutex`+`Condvar` turnstile, or a `BinaryHeap`-based reorder gate) until every earlier sequence number has already been applied, then calls `Ingestor::ingest_event` and publishes the broadcast update, then signals the next sequence number's turn. This serializes only the (fast, already-lock-guarded) *apply* step, not the I/O, so two connections' reads still proceed fully in parallel. Alternative considered: a single dedicated worker thread that all connections feed via an `mpsc::Sender<ReportEvent>` after their own read/parse completes - rejected because the channel's arrival order is still determined by each thread's independent read+parse latency, which is exactly the race causing the bug (a larger `UserPromptSubmit` payload parses slower than a tiny `PreToolUse` payload), so it would not actually fix the problem it's meant to fix. Alternative considered: do the read+parse+apply entirely on the single-threaded accept loop (no per-connection thread at all for `ReportEvent`) - rejected because a hung/slow connection would then stall the daemon from accepting *any* other connection, including unrelated agents' events, which today's per-connection-thread design deliberately avoids.

**Bounded read timeout on `ReportEvent` connections:** set a read timeout (e.g. 500ms, mirroring `agentmon-report::SEND_TIMEOUT`'s existing value and rationale) on each accepted stream before reading its message. Without this, a connection that accepts but never finishes sending its payload would hold its turnstile slot forever, blocking every later-numbered connection's apply step indefinitely - reintroducing, for that one pathological case, the cross-agent stall the per-connection-thread design exists to avoid. A connection that times out is treated the same as today's malformed-payload case (rejected, logged, turnstile slot released immediately so later sequence numbers proceed) rather than propagated as a panic.

**Scope of the ordering fix:** only `ClientMessage::ReportEvent` goes through the turnstile. The other message types (`ReportTestRun`, reminder commands, etc.) keep calling straight into `Ingestor` from their own connection thread, unchanged - they are not implicated in the reported bug, and serializing them too would add complexity (and a small amount of added latency to reminder/test-run actions) for no behavioral benefit.

**Prompt-entry text:** drop the `with_category_word`-equivalent hardcoded `"🗣️ prompt submitted"` base text in `log_status_cell_text_and_style`'s `LogCategory::Prompt` arm down to just the emoji, and change `log_entry_status_line` so the prompt snippet becomes that entry's entire remaining text (no leading `" — "` separator, no surrounding quotes) rather than being appended after it - the `Agent` category's handling (quoted, em-dash-prefixed snippet after its existing "🤖 agent started/done" text) is untouched, since that snippet is secondary context on an entry whose primary content is the status word, whereas a prompt entry's primary content *is* the prompt. The underlying `LogEntry.status` value stays the literal string `"submitted"` (used by the Logs tab's status filter/sort) - only the rendered text changes.

**Full-prompt modal is reachable only from the details modal's Logs pane, not the top-level Logs tab:** add `App.prompt_detail: Option<String>` (the full prompt text) as an independent overlay field - not a new `Modal::PromptDetail(String)` variant - because it must be reachable while `app.modal` is already `Some(Modal::Details(_))` without disturbing it, exactly the constraint `reminder_form`/`confirm_delete_reminder` already solve the same way. Checked early in `input.rs::handle_key` (same precedence tier as `reminder_form`): while `Some`, only `Esc` (clear it), `j`/`k`/`g`/`G` (scroll), and the global `q` (quit, unchanged - this is a read-only view like `Modal::Help`, which `q` already isn't special-cased for) do anything. Only `handle_modal_key`'s `ModalFocus::Logs` arm opens it: category `Prompt` on the pane's selected entry opens `prompt_detail`, regardless of whether its displayed snippet happens to be truncated; any other (non-prompt) entry there is a no-op, unchanged from before this modal existed. `handle_logs_tab_key`'s `Enter` arm is **not** touched - it keeps unconditionally calling `open_details_modal()` for every entry, prompt-category or not, truncated or not, the same as every other row in that tab. (An earlier draft of this change diverted the top-level Logs tab's `Enter` too, for a truncated prompt entry; that regressed the normal "open details modal" path for the entry type the Logs tab is otherwise consistent about, so it's reverted - see the next decision for the actual fix this surfaced.)

**Dropped the truncation check in the Logs pane too, for the same consistency reason:** an earlier draft gated the pane's `Enter`-opens-`prompt_detail` behavior on `prompt_snippet(text) != text` (i.e. only when the row's snippet was actually cut off). Removed per explicit user feedback: requiring the user to visually judge whether a row's text was truncated before knowing what `Enter` would do is exactly the kind of inconsistency this change's Logs-tab revert (previous decision) already moved away from at the top level - a prompt entry's `Enter` now always means "show me the full text," never "maybe nothing, depending on how long it looked." This removes `prompt_entry_snippet_is_truncated` (`crates/agentmon/src/input.rs`)'s only remaining call site; since nothing else in the codebase needs a truncation check (the top-level Logs tab's `Enter` never used one either), the function itself, its unit test, and its now-unused `use crate::ui::prompt_snippet;` import should all be deleted rather than left as dead code.

**The details modal's Logs-pane selection must stop depending on whether it needs to paginate:** `render_details_modal`'s `selected` computation (see the Context section's note on the current code) drops its `paginated &&` clause, keeping only the focus check and a non-empty check: `let selected = if matches!(app.modal_focus, ModalFocus::Logs) && !project_logs.is_empty() { Some(app.modal_logs_pagination.display_selected(project_logs.len())) } else { None };`. The scrollbar and the title's pagination-keys hint stay exactly as conditional on `paginated` as before - only the highlighted-row visibility changes. This is the actual fix for reaching the full-prompt modal in the common case (a project with only a few log entries, no pagination needed): without it, `Enter` in the pane had no selected index to read regardless of which entry category triggers which action. Alternative considered: special-case the `selected` computation only when the entry at index 0 is an actionable (truncated prompt) entry, leaving every other single-page case unselected - rejected as inconsistent (a user navigating the pane with `j`/`k` would see a selection sometimes appear and disappear depending on what's at the top of an unpaginated list) and more complex than simply always showing it once there's at least one entry.

**Scrolling, not truncating, inside the full-prompt modal:** a simple `usize` scroll offset on `App`, clamped to the wrapped line count less the modal's visible height, advanced by `j`/`k`/`g`/`G` the same as every other scrollable list in this TUI - no new widget, just `ratatui::widgets::Paragraph::scroll`.

## Risks / Trade-offs

- [Turnstile adds a small amount of latency to event application under concurrent load] -> Acceptable: hook events are human-paced (at most a handful per second even across many agents), and the apply step itself is already sub-millisecond (in-memory registry/log updates); the turnstile only ever makes a thread wait for *already-parsed, about-to-be-applied* work ahead of it, never for another connection's I/O.
- [A read timeout changes today's unbounded-wait-then-drop behavior for a hung `ReportEvent` connection to a bounded-wait-then-drop] -> This is strictly a tightening, not a behavior users could be relying on, and matches the existing client-side `SEND_TIMEOUT` philosophy already documented in `agentmon-report`.
- [Removing the "prompt submitted" wording changes a string the Logs tab's Status filter cycles through for display, even though the underlying filter value (`"submitted"`) is unchanged] -> Low risk: the filter's displayed hint text already just echoes the raw status strings present in the log; verify this during implementation and adjust the hint rendering if it assumed status-word text matched the rendered line.
- [The daemon-side fix narrows the race but - absent a way to reproduce the user's exact "always" report in a test - can't be proven to fully eliminate every path to misordering] -> Flagged for the user directly: the fix closes the one concrete, verified mechanism found by inspecting `server.rs`'s threading model; if misordering is still observed after this ships, that would point to something outside what was found here (e.g. an assumption about Claude Code's own hook-blocking behavior that doesn't hold), and would need a fresh look with that evidence in hand.
- [Always showing a selection in the Logs pane changes its appearance for every project with activity, not just ones with a truncated prompt entry to select] -> Intended, not a side effect to mitigate: the pane already supports selection and `j`/`k`/`g`/`G` navigation once paginated, so a single-page pane now simply behaves the same way the Agents tab's own table already does (always selectable when non-empty) rather than being a special case.
- [Opening the full-prompt modal for a prompt entry whose snippet was already short shows text identical to what the row already displays] -> Accepted as the cost of consistency, per explicit user feedback: the alternative (truncation-gated) behavior required the user to visually judge a row's length before knowing whether `Enter` would do anything - a worse inconsistency than a harmless modal that echoes already-visible text.
